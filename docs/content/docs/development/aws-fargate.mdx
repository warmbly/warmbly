The configurations in `deploy/terraform/` manage infrastructure through separate
AWS, PlanetScale and Confluent state files. The AWS root prepares infrastructure
in `us-east-1`: a network, ECS cluster, repositories, logs, configuration stores,
Valkey and optional database connectivity and certificates. The separate runtime
root creates application services, task roles and HTTPS ingress. The worker root
prepares ARM EC2 hosts with static IPs. Public traffic changes remain a separate
cutover step.

## Adopt existing resources

The PlanetScale root adopts an existing Postgres branch and reads its database
metadata. The Confluent root adopts an existing environment, Basic Kafka cluster
and service account, and reads Schema Registry metadata. Each uses import blocks
and destruction guards. An adoption plan must show imports with zero resource
creates, updates, replacements or deletes before it is applied.

Importing configuration does not copy SQL rows, Kafka messages or consumer
offsets. SQL migrations, schema versions, access rules and runtime worker topics
retain their current owners. Existing credentials are provisioned separately
from Terraform.

## Keep existing data services

Warmbly can run its control plane on Fargate while keeping PlanetScale Postgres,
Confluent Kafka, S3 and AWS KMS. Keep the existing KMS key available so stored
organization data keys remain readable. Workers continue to use the brokered
interfaces described in [split deployment](/development/split-deployment/).

PlanetScale Postgres supports an interface VPC endpoint in the database's AWS
region. Set `planetscale_service_name` from the branch's Private Service Name.
The foundation creates endpoint interfaces in two availability zones and limits
database access to the application security group. Use the branch's Private
Host with certificate verification in application connection strings.

Creating an endpoint does not disable the database's public access. Change public
access restrictions only after every database client, including operational
tools, has a working private path.

### Database connection pooling

PlanetScale includes a local PgBouncer with each Postgres database. It uses the
same hostname and credentials on port `6432`, including through PrivateLink.
Dedicated PgBouncers are a separate paid option. See
[PlanetScale's connection pooling documentation](https://planetscale.com/docs/postgres/connecting/pgbouncer).

The local pooler uses transaction pooling. Route migrations and operations that
hold session advisory locks through a direct connection on port `5432`.
Set `PRIMARY_DB` to the pooled connection, `PRIMARY_DB_DIRECT` to the direct
connection and `DB_POOL_MODE=transaction` for the Go services. Cloud reconciliation
and managed operations open direct sessions for their session locks. Backups and
the migration binary also use the direct connection. Before enabling transaction
mode, configure the application database roles with `statement_timeout=60s` and
`idle_in_transaction_session_timeout=5min`. The Go client verifies those effective
settings instead of sending timeout startup parameters to PgBouncer. Verify the
actual realtime client's prepared statements separately before switching it.

Budget Postgres server connections across every database role, direct client and
deployment replica. PgBouncer's `default_pool_size` applies per user/database
pair, so separate service roles can each create a server pool. Its client
connection limit is not additional Postgres server capacity. Preserve headroom
for migrations and operations throughout the overlap with the old deployment.

Confluent Kafka PrivateLink requires an Enterprise or Dedicated cluster. Keep the current
Kafka transport, codec, topics and consumer groups during a compute migration.
Check connectivity for both Kafka and Schema Registry. External workers need
their own network path if the cluster becomes private.

Keep existing tracking hostnames registered with the edge provider, including
their TLS certificates and origin configuration. Put those hostnames in
`tracking_additional_hosts` so the ALB forwards their original Host headers to
the tracking service. The empty default keeps ordinary single-host deployments
unchanged. Validate each hostname before moving its traffic.

## Size tasks from measurements

Fargate bills provisioned CPU and memory. Its smallest Linux task has 0.25 vCPU
and 512 MiB. Use more CPU when measured peaks exceed that allocation and allow
memory headroom for startup and bursts. ARM64 images can reduce compute cost;
verify that every pinned image includes that architecture, including Kafka
variants.

Keep the shared Redis-compatible cache separate from replaceable app tasks. It
coordinates multiple services and workers, so inspect all callers before
changing its endpoint. Size the database from its own utilization and query
metrics rather than from application container memory.

The AWS root provisions one Valkey `cache.t4g.micro` with TLS, encryption at rest,
password authentication and one-day snapshots. It uses the standalone protocol
supported by Warmbly's current clients and multi-key scripts. ElastiCache
Serverless requires cluster-aware clients and different multi-key handling.
The single-node configuration has no replica failover.

The new cache starts empty. Shared counters, locks and transient state need a
coordinated transition before clients switch endpoints. Its private endpoint is
reachable from application tasks in the VPC; external workers and local tools
need a private route or tunnel.

Budget for load balancing, public IPv4 addresses, cache, interface endpoints,
logs, secrets and transfer charges in addition to Fargate compute. The foundation
starts no NAT gateway or load balancer. PrivateLink does not replace internet
egress for other application dependencies.

The runtime root uses public task IPs for egress and restricts inbound application
traffic to its load balancer. Start with zero desired tasks until configuration
and dependency checks pass. A Linux task with 0.5 vCPU requires at least 1 GiB of
memory; the 512 MiB minimum applies to 0.25 vCPU tasks.

Mail workers can remain on existing hosts or use the separate EC2 worker root.
Graviton `t4g.small` hosts provide 2 vCPUs and 2 GiB of memory with a static public
IP per worker. The root uses standard CPU credits to cap burst charges. Bootstrap
prepares each host without starting its worker, so identity and credentials can
be checked before a sequential handover. Check mailbox authentication when the
outbound IP changes, and preserve each worker ID throughout the move.

## Prepare configuration

Use the deployment README to bootstrap encrypted, versioned Terraform state and
apply the foundation. Installation-specific values and plans belong outside the
checkout. Use Standard String parameters in Systems Manager Parameter Store for
approved non-secret values such as public URLs, provider names and feature
switches. Put passwords, tokens, encryption material and credential-bearing
connection strings in Secrets Manager. Reference both stores from ECS task
definitions. Running tasks must be replaced to pick up updated injected values.

The foundation also creates a separate rotation secret. It holds the state of a
[key rotation](#rotate-keys) in progress, including the pending and previous
values, so the rotator task can resume or undo it. Keep that secret restricted
to operators and the rotator; the deployment role reads no secret value.

Preserve current configuration before preparing replacements. Keep a dependency
map of each value's readers, encrypted data and rollback requirements. The
Valkey password uses an ephemeral Terraform read and a write-only authentication
argument, so its value is omitted from Terraform state and saved plans.

Use ECS task roles for S3, KMS and SES access. Give the execution role permission
to retrieve only its service's runtime configuration. Backend and consumer need
application permissions; worker nodes use brokered operations and carry no cloud
credentials.

## Coordinate the cutover

1. Verify backups and a restore procedure, including the keys needed to read
   encrypted data. Pin compatible release images and prepare TLS certificates.
2. Create separate database roles and Kafka credentials for the new deployment.
   Verify access before retiring credentials used by the running deployment.
3. Configure a shared cache and internal service addresses. Verify that workers
   can reach every dependency they require.
4. Run the release's migration task and require a successful exit before starting
   the backend. Set `DB_MIGRATIONS_ON_START=false` in its runtime configuration.
   The backend and consumer verify schema readiness before starting work. Coordinate
   scheduler ownership before allowing old and new backends to run scheduled work
   together. Confirm compatibility before sharing a database across releases.
5. Start the remaining services. Check API access, forms, tracking, websocket
   authentication, Kafka processing and worker heartbeats. Set a stop timeout of
   at least 60 seconds for services that drain work.
6. Move public traffic to healthy targets, drain the previous deployment and
   confirm that queued work has completed. DNS changes can leave some clients
   on the previous address until caches expire.
7. Retire old credentials after all callers use replacements. If rollback is
   needed, use the replacement credentials on the rollback deployment too.

Authentication key rotation invalidates existing signed tokens and requires
users to sign in again. MFA secrets are encrypted with `TWOFA_SECRET`, which
falls back to `AUTH_SECRET` when unset. Coordinate re-encryption with key changes
so enrolled MFA remains readable. Mailbox encryption key changes likewise need
an explicit re-encryption and worker rollout procedure.

Treat database logins and data encryption keys as separate changes. A replacement
database login connects to the same stored data; it does not require new mailbox
passwords or OAuth grants. Preserve the existing credential encryption key,
organization data keys and their KMS decrypt capability during the hosting
cutover. Keep OAuth application identities and authorized callback URLs
compatible with existing refresh tokens.

Before activating replacement encryption keys, verify decryption of the stored
mailbox credentials, OAuth tokens, webhook secrets, integration credentials and
MFA enrollments without logging their contents. Include instance-level data and
pending mailbox-erasure tokens in the inventory. Repeat these checks using the
new tasks' runtime permissions before moving traffic; operator access alone does
not verify a task role. Re-encryption must preserve the underlying credential
values and coordinate all readers, writers, queued work and rollback deployments.

`AUTH_SECRET` also derives signing keys for unsubscribe links and domain ownership
proofs. Plan compatibility for previously issued links and existing DNS proofs
before changing it. A successful sign-in check alone does not verify these paths.

The infrastructure foundation alone does not provide a zero-outage migration.
Credential rotation, scheduler ownership, shared state and connection draining
must all be coordinated before the traffic switch.

## Deploy releases

Once the cutover is done, releases reach production on their own. A stable tag
(`vX.Y.Z`, never a prerelease) builds and publishes the images, and the release
workflow then calls `.github/workflows/deploy-aws.yml` for that tag when the
repository variable `AWS_DEPLOY_ENABLED` is `true`. Set it to anything else to
stop automatic deploys; nothing else changes. Deploys, key rotations and
Terraform applies share one queue, so only one change reaches production at a
time and none is cancelled by the next.

Terraform owns the shape of every task definition (environment, secret
references, sizes, health checks) and the workflow owns only the image. A deploy:

1. Checks that the tag's commit is on `main`, that every image digest carries
   build provenance from the release workflow, and that the tag is not older
   than the one running.
2. Registers a revision of each service from its latest Terraform revision with
   the release's digests, choosing the `-kafka` image where the task definition
   says so, and refuses one that would stop referencing a secret the running
   service reads.
3. Runs the dependency validation task, then the migration task on the backend's
   image. Either failing stops the deploy before any service moves.
4. Rolls backend, then consumer, then forms, tracking and realtime together.
   Each service is watched for a bake (five minutes by default) after it is
   stable.
5. Starts a [canary rollout](/development/warmblyctl/#fleet) of the worker and
   consumer hosts from the `ops` task. The first host moves alone and the rest
   follow after it has stayed healthy for five minutes by default. Every host
   must then finish the same healthy-uptime bake before the rollout completes.
   Two stages therefore need at least ten minutes, plus image pulls, restarts
   and heartbeat delivery. Missing heartbeats, host rollback and repeated
   restarts still stop admission. Self-hosted CLI rollout defaults remain
   unchanged at 30 minutes per stage.

The fleet-start task retries an image-pull failure at most twice, after 30 and
60 seconds, only when ECS confirms the task stopped before its command ran.
It reuses the exact task definition and command with an idempotent token per
attempt. An executed command failure or unresolved task requires inspection;
migration tasks are never automatically retried by this recovery path.

During the bake, a service fails when one of its alarms fires or ECS rolls it
back. Each public service has two alarms, which ECS also uses to roll back on
its own: more than 5% of requests answered with a 5xx in two of three minutes
(counted only once a minute sees at least 20 requests), and any unhealthy target
for three minutes. A failure at any step puts every service already moved back
on its previous revision and task count, newest first, and the run fails with a
summary. The schema stays where the migration left it, which the previous
release reads.

### Redeploy, roll back or change a secret

Dispatch **Deploy AWS control plane** from the Actions tab:

| Mode | Use it to |
|---|---|
| `redeploy` | Roll the running release again, for example to pick up task definitions Terraform changed |
| `rollback` | Go back to an earlier release. The migration is skipped and the fleet follows in a canary rollout |
| `deploy` | Deploy a release by hand, for example while `AWS_DEPLOY_ENABLED` is off |
| `refresh-secrets` | Roll out a value changed in Secrets Manager, such as a database password or a third-party API key. Leave the tag empty to keep the running images |

`refresh-secrets` repins every secret reference to the version currently marked
`AWSCURRENT` and rolls with the same bake and rollback, so a wrong value is
caught and put back like a bad release. Change the value in Secrets Manager
first; the workflow only ever sees version ids. Nodes on worker hosts pick up a
change to a value they hold once their env refreshes
([keeping a node's env current](/development/configuration/#keeping-a-nodes-env-current)).

`services` limits a run to some of the five services, and `bake_seconds` changes
the ECS service bake. `fleet_bake_seconds` sets the healthy uptime required per
worker stage, from 300 through 3600 seconds. Automatic releases use the
`AWS_FLEET_BAKE_SECONDS` repository variable, defaulting to 300. Set it to 1800
for a longer observation window. This changes future rollouts; the policy of an
active rollout stays fixed. Releases published before build provenance existed fail the provenance
check; dispatch those once with `require_attestation` off. The automatic
redeploy after a Terraform apply cannot turn it off, so until a release with
provenance is running it stops at that check and changes nothing.

## Rotate keys

Dispatch **Rotate instance keys** from the Actions tab and choose a key and an
action. A rotator task inside AWS generates the replacement, writes it as a new
secret version and reports only version ids, so no key passes through GitHub or
a log. The workflow then rolls the services onto those versions, waits for the
worker and consumer hosts to apply their new env, and runs `warmblyctl` in the
`ops` task to prove each step before the previous value is retired.

| Key | What a rotation does |
|---|---|
| `INTERNAL_API_TOKEN` | The backend accepts the previous token for up to seven days while tracking, forms and the hosts move to the new one, then it is retired |
| `NODE_BROKER_TOKEN` | The same, for the hosts' broker routes |
| `CREDENTIALS_ENCRYPTION_KEY` | The new key is first made readable everywhere, then made primary, stored values are resealed under it, and the old key is retired once `warmblyctl keys status` finds nothing left under it |
| `TWOFA_SECRET` | The new secret seals new enrollments, existing ones are resealed, then the old secret is retired |
| `UNSUBSCRIBE_SIGNING_SECRET` | New links are signed with the new secret. Links already in inboxes stay valid for a year, so the old secret is kept for reads until then |

`rotate` runs every step it can prove safe in one run. It stops, and says what
it is waiting for, when hosts have not applied the new env within
`node_wait_minutes` (30 by default) or values still open only under the old key.
Run `rotate` again to continue, or `retire` once the reason has cleared.
`retire` refuses while it still has a reason to. `abort` puts the previous value
back as primary; a replacement key that may already have sealed or signed
something stays readable. `status` reports where a rotation stands. Only one key
rotates at a time.

The [Keys tab](/development/admin-panel/#instance) under Configuration in the
admin panel shows the same checks without starting anything.

### Before the first rotation

Each service reads the previous value from an overlap key that has to exist and
be referenced before a rotation can use it:

1. Run the workflow with `prepare` for the key. It adds the empty overlap keys
   (such as `INTERNAL_API_PREVIOUS_TOKENS` and `INTERNAL_API_PREVIOUS_UNTIL` on
   the backend) to every service that reads the key, and lists those services.
2. Add those names to each listed service's `secret_keys` in the runtime var
   file and apply the runtime stack.
3. Confirm the backend runs a release deployed by the workflow. A rotation rolls
   the running release, and a backend started any other way carries no release
   tag to roll.

A rotation leaves the services pinned to newer secret versions than the runtime
var file names. Deploys always use the newest pin, so nothing reverts, but
update the version ids in the var file afterwards to keep Terraform's revisions
current. Authentication keys (`AUTH_SECRET` and realtime's `JWT_SECRET`) are not
offered: they have no overlap, and rotating them signs everyone out.

## Run Terraform from CI

Changes to `deploy/terraform/aws/` are planned and applied by
`.github/workflows/terraform-aws.yml`. Var files never enter the repository;
they live in the private state bucket, every value in them is masked before
Terraform runs, and only resource addresses and actions are printed. No full
plan reaches a log, a comment or an artifact.

- A pull request from this repository gets one comment with the runtime and
  workers plans. The foundation plans on merge, because it reads the cache
  password, which the plan role may not.
- On merge, each stack is planned in order: foundation, runtime, workers. A
  stack that only creates and updates applies on its own. One that replaces or
  destroys anything stops and waits for approval in the
  `aws-infrastructure-approval` environment, and the stacks after it wait too.
  On approval it plans again and applies only if the plan is still the one that
  was approved. A new task definition revision counts as an update, because the
  previous revision is kept.
- When an apply changes a service's task definition, the running release is
  redeployed so the change reaches the services.

The bootstrap stack stays manual. So does any change to the CI roles themselves: the apply role cannot
change its own permissions or trust, or the plan role's, so an administrator
applies those by hand.

## Encrypt traffic inside the VPC

The load balancer terminates the public TLS connection. With `target_tls` set,
the hops behind it are TLS too: the load balancer reaches each task over HTTPS
with HTTPS health checks, and the forms and tracking services reach the
backend's internal API at `https://backend.<namespace>:<target_tls_port>`,
verifying its certificate. The services read the settings described under
[TLS listeners](/development/configuration/#tls-listeners).

The two hops trust different things. A load balancer does not validate its
targets' certificates, so forms, tracking and realtime serve a certificate
generated in memory at boot. The forms and tracking services do verify the
backend, so it serves a certificate you supply, and they trust exactly that
certificate (`BACKEND_INTERNAL_CA`) rather than any public authority. The
internal hop stays on the private service-discovery name, so the internal API
token never leaves the VPC.

### Prepare the backend certificate

Create a key pair naming the private host. Use the runtime `namespace`
(`warmbly.internal` by default):

```bash
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes -days 825 \
  -subj "/CN=backend.warmbly.internal" \
  -addext "subjectAltName=DNS:backend.warmbly.internal" \
  -addext "basicConstraints=critical,CA:FALSE" \
  -addext "keyUsage=critical,digitalSignature" \
  -addext "extendedKeyUsage=serverAuth" \
  -keyout key.pem -out cert.pem
```

Add the contents of `key.pem` to a new version of the backend secret as
`SERVE_TLS_KEY`, add `SERVE_TLS_KEY` to the backend's `secret_keys` and point
its `secret_version_id` at that version. Put the contents of `cert.pem` in the
runtime var file as `backend_internal_certificate`; it is public. The plan
refuses `target_tls` without both. Replace the pair before it expires: the
backend logs a line at boot inside the last 30 days, and an expired certificate
stops click tracking and hosted forms.

### Move through the stages

`target_tls` takes six values. Change it one stage at a time, and let each
merge finish its apply and redeploy before the next:

| Stage | What changes |
|---|---|
| `off` | Nothing; tasks serve plain HTTP only |
| `serve` | Every load-balanced task also serves TLS on `target_tls_port` (default `8443`), and the security groups open that port to the load balancer and between tasks. Traffic is unchanged |
| `both` | An HTTPS target group per service is attached to its listener rule at weight 0 and the tasks register in both groups. The forms and tracking services move to the backend's TLS port |
| `route` | Listener rules forward to HTTPS and alarms watch the HTTPS groups. The HTTP groups, healthy registrations and network rules remain ready while the new path bakes |
| `drain` | After the route deployment and bakes pass, ECS stops registering HTTP targets and listeners drop their HTTP references. The groups and network rules remain while connections drain |
| `on` | After the drain deployment and bakes pass, the empty HTTP groups, the plain-port security group rules and the internal `8080` rule are removed. Every plain listener is bound to loopback for the container health check only |

Each stage keeps the listeners the previous one used, so a rolling deploy never
meets a task that cannot answer. `serve` and `both` only add task definition
revisions and resources, so they apply on their own. `route` performs the traffic
switch without deleting network rules or target groups. It must finish its normal
release redeploy and bakes before a separately approved `drain` run. Cleanup checks
that the HTTP groups have no load balancer references or registered targets and
that every public service uses only its HTTPS target group. ECS waits for a steady
state during these stages.

Before `serve`, the running release has to support `SERVE_TLS`. An older image
ignores the setting and keeps working in `serve`, but not in `both` or `on`, so
advance past `serve` only once rolling back to a release without it is no longer
needed. A stage can be undone by setting the previous one while the current
one is `serve` or `both`. From `route`, returning to `both` sends traffic to the
still-registered HTTP targets. From `drain`, return to `route` first and wait for
healthy HTTP registrations before returning to `both`. Stepping back from `on` is not supported, because it
would forward to an HTTP target group that has no tasks yet; roll back images
among releases that support `SERVE_TLS` instead.

### Finalize TLS independently

The manual **Finalize runtime TLS** workflow advances `both` to `route`, then
`drain` and `on` in separate approved runs without applying other infrastructure
changes. After verifying the pinned backend hop
and every HTTPS target, upload the reviewed `both` runtime var file to
`warmbly/production/vars/runtime-tls.tfvars.json` in the private state bucket.
Keep its S3 version ID: the workflow reads that exact version in both jobs.

Dispatch the workflow from `main` with stage `route`, that version ID and the
currently deployed release tag. It prints resource addresses and actions for review and
waits in `aws-infrastructure-approval`. After approval it rechecks HTTPS target
health, replans and requires the complete resource changes to match the approved
digest. Each job first requires all four services to be stable on the selected
release with compatible TLS listeners and registrations. Route also requires
healthy HTTP fallback targets. Route and drain plans refuse target-group and security-rule deletions. The scope
guard refuses changes to other task definitions or infrastructure.

After applying, it redeploys the same release to backend, forms, tracking and
realtime through the normal attestation, secret comparison, alarm and bake gates.
It does not start a worker rollout. After that run succeeds, persist
`target_tls=route`, verify HTTPS health and routes, and upload a new versioned
snapshot. Dispatch stage `drain` with that snapshot and the successful route run ID
as `previous_run`. After the drain run succeeds, persist `target_tls=drain`, upload
a new snapshot, and dispatch `on` with the successful drain run ID. Each stage
verifies the preceding workflow completed all bakes. Cleanup is refused until
HTTP references and registrations have drained. Review and approve each
plan separately. Persist `target_tls=on` only after it succeeds, then verify the
effective loopback listeners and HTTPS routes.

### Validate recovery evidence

The read-only recovery validators keep a recovery contract separate from the
normal route, drain and on transition checks. They do not provide a production
recovery execution workflow. The baseline identifies four drained HTTP groups
and their reviewed state projection. `check-state` verifies a supplied raw
Terraform state file against the baseline SHA-256, lineage, serial and exact
group identities. `check-plan` permits only the four corresponding deletions
without refresh drift. The baseline and state version must come from a trusted,
reviewed collection process; matching a file hash alone does not establish that
provenance.

`runtime-tls-recovery-lineage.sh` collects and checks the GitHub portion of a
recovery contract. Its version 1 contract names `warmbly/warmbly` and three
identities, `release`, `drain` and `failedOn`, each with a stable release `tag`,
40-character commit `source`, numeric `runId` and numeric `attempt`. The current
release is distinct from the historical release retained by both TLS runs.
Collection reads the exact run attempts and the complete failed ON job inventory.
It requires the current release and historical drain to have succeeded, the ON
apply to have succeeded before a failed redeploy, and each workflow path, branch,
title and source to match its declared role. The local checkout must include the
release tag and full commit history so the checker can verify the tag and
drain-to-ON-to-release ancestry. Collection writes a new private directory and
refuses to overwrite a prior collection.

These checks neither relabel an earlier release's drain nor change the normal
workflow's predecessor requirements. A complete recovery workflow must also
collect current service, TLS, route and target health, bind the immutable vars
snapshot and state version, and preserve separate protected approval, production
serialization, plan digest comparison, attested redeployment and final effective
verification. Do not use these validators as an alternative to those gates.

## One-time GitHub setup

1. On the `aws-production` environment, allow the `v*.*.*` tag pattern next to
   `main` in deployment branches and tags, and add a tag ruleset so only release
   managers can create `v*` tags.
2. Set `terraform_ci = true` (with `github_repository`) in the runtime var file
   and apply it once by hand. Its `terraform_role_arns` output names the plan
   and apply roles.
3. Upload `foundation.tfvars.json`, `runtime.tfvars.json` and
   `workers.tfvars.json` to `s3://<state bucket>/warmbly/production/vars/`.
4. Create three environments: `aws-infrastructure-plan` with no branch limit,
   because pull requests plan in it and its role only reads, `aws-infrastructure`
   limited to `main`, and `aws-infrastructure-approval` limited to `main` with
   required reviewers.
5. Set these variables. `AWS_DEPLOY_ENABLED` and `AWS_TERRAFORM_ENABLED` have
   to be repository variables, because job conditions read them before any
   environment applies:

| Variable | Value |
|---|---|
| `AWS_DEPLOY_ENABLED` | `true` to deploy stable releases automatically |
| `AWS_DEPLOY_ROLE_ARN`, `AWS_ECS_CLUSTER`, `AWS_ECS_SERVICE_PREFIX` | Runtime outputs, on the `aws-production` environment as the runtime README describes |
| `AWS_TERRAFORM_ENABLED` | `true` to plan and apply from CI |
| `AWS_TERRAFORM_PLAN_ROLE_ARN` | The `plan` entry of `terraform_role_arns` |
| `AWS_TERRAFORM_APPLY_ROLE_ARN` | The `apply` entry of `terraform_role_arns` |
| `AWS_TERRAFORM_STATE_BUCKET` | The state bucket name |

Hand each worker host's updates to the fleet once its worker runs, with the
`--adopt --env-refresh` step in the workers README. Until then it neither follows
releases nor receives rotated values.
